# Recall Drill

History-taking recall game (the built-in playlists are Conditions, Presentations and Systems review), a React single-page app served at the site root, https://medpunk.oyc.id.au (React Router, no basename). Drills are quizzes stored in the database and loaded from the API (see "Quizzes and playlists" below). `conditions.json`, `presentations.json` and `systems-review.json` are the seed data that `scripts/seed-builtins.mjs` turned into the built-in quizzes; they are no longer bundled or read by the app.

Routes: `/` (home: the three default playlists, each with its description and a `done/total` counter, then the Minis section, with History on the right), `/p/<playlistId>` (a playlist: its quizzes under the playlist's section headings, who made it, Random and a Starred filter, and a History panel limited to that playlist; the header title links home), `/login`, `/settings` (also `/profile`), `/q/<quizId>` (the drill). Ids are UUIDv7 strings. Old links still work: `/p/cond|pres|sys` redirect to the built-in playlists and `/q/<base64 of "<system>.<name>">` is looked up by its name with `GET /api/quizzes?name` and redirected (quizzes no longer have a system, so the system part is ignored; with several quizzes of that name the oldest, the seeded built-in, wins) (`lib/legacy.js`, which also holds the three built-in playlist ids, `FEATURED`). An unknown id shows "Drill not found" / "Playlist not found"; a deleted quiz shows "This quiz was deleted by its owner." and can't be played. History and stars are keyed by quiz id (`history.quiz_id`).

The root `index.html` (the `main` entry in `/vite.config.js`) is a thin shell that loads `src/recall-drill/main.jsx`; Cloudflare serves it for every path that isn't a real file (`assets.not_found_handling: "single-page-application"` in `wrangler.jsonc`). The app used to live under `/recall-drill/`: those paths are routed to the Worker (`run_worker_first`), which 301s them to the same path at the root. Minis are separate pages under `/mini/<name>` (`mini/<name>.html`).

Layout: `routes/` (Home, Playlist, Drill, Login, Settings), `components/` (Layout with the account menu, Avatar, Owner, DrillActions, DrillList, History, Minis (a `MINIS` array of cards linking to the standalone pages under `/mini/`: Dermatome Ninja and the five case quizzes)), `state/` (`AccountContext` user record + saving, `FilterContext` the browsed playlist and starred filter, which decide what Random/Next/New pick from, `useDrillGame` the round logic), `lib/` (`api.js` fetch helper, `content.js` hooks that load playlists and quizzes, `data.js` builds the game's drill from a quiz, `match.js` keyword matching, `legacy.js`, `storage.js`, `auth.js`, `confetti.js`), `recall-drill.css` (plain CSS, not Tailwind).

## How the game works

1. The player picks a playlist (Conditions / Presentations / Systems review), then a drill (random, or from the list, grouped by the playlist's sections).
2. The items appear as numbered face-down tiles, grouped in the quiz's sections (free-form: a quiz's sections are the keys of its `items`, shown with the first letter capitalised, so nothing in the code knows about "conditions" or "presentations"). The built-in Conditions quizzes have five sections: Presentation, Risk factors / etiology, Examination findings, Investigations (tests for diagnosis and monitoring only, with the key finding: specific and high-yield), Medications, treatment, and management (drugs plus the essential non-drug management, e.g. podiatry/offloading, CPAP, pulmonary rehab). The built-in Presentations quizzes have three: Differentials, Associated features (history), Investigations; Systems review quizzes have one: Symptoms to ask about. Heading icons are matched by section name (`SECTION_ICONS` in `lib/data.js`); other names have no icon. The Reveal button reads `Reveal <section name>`.
3. The player types one item at a time. Each input is tested against every item's `keywords` regex; a match flips that tile. Matching is live (on input) and on Enter. "New" jumps to another random item.
4. The action buttons sit on two lines: the first has the Reveal button and a square borderless `↺` Drill icon (`.redo.bare`, same height as Reveal; it drills the open section when collapsed, else the last section with missed tiles, and is hidden until something has been revealed, dimmed when nothing is missed), the second has Hint, Back and New. One button (first row) reads "Reveal <next section>" (e.g. "Reveal differentials"); each click reveals that section's missed tiles, and revealing the last one ends the round. Naming every tile in a section by typing fires confetti and moves the button on to the next section. The player can click a revealed missed tile to credit it (on touch devices a tap opens the tile menu instead, whose first entry is "I got this"). Score is found+credited / total items. The sliding Collapse | Expand toggle by the counter (the highlighted segment is the current state; remembered in localStorage `recallDrillCollapsed`). Expanded (default): every section is open, typing is matched against all tiles, and Reveal goes through the sections in order. Collapsed: one section is open at a time (initially the one Reveal names); typing is matched only against it and Reveal reveals just its missed tiles and leaves it open, but the counter, section counts and score always cover every section. Clicking a collapsed heading switches to it; clicking the open one does nothing. Completing a section never ends the round; it ends when every tile has been named or revealed, and then all sections are shown.

Right-click menu: right-clicking a revealed tile (not a face-down one), or tapping it on a touch device (`(hover: none)`, as there is no right-click; a mouse click still credits), opens `TileMenu` (`components/TileMenu.jsx`) at the cursor with I got this / I didn't get this (credit toggle), Ignore / Restore and, for signed-in users, Teach new keyword (a modal that shows the item's current keywords and appends the new comma-separated keywords, minus duplicates, as `|a|b` to its keywords), Edit (a modal for label and keywords) and Delete (red; asks with the custom confirm dialog, then removes the item from the quiz). Teach, Edit and Delete save the whole quiz with `saveQuiz` (`lib/editItem.js` finds the stored item by section, category and label) and update the round's own item in place, so matching changes at once. Delete takes the tile out of the round with `removeItem` from `useDrillGame`, which splices `drill.items` and renumbers every tile-index set, so the round keeps its progress.

Drill: once a section has missed tiles (revealed, not found, credited or ignored; recalled tiles still count, so a section stays drillable after a successful drill, and starting a drill clears their recalled state), a single square `↺` button (`.redo`) appears in its heading, left of the "X of Y" count. It hides those tiles again so they can be typed; tiles answered become **recalled** (purple, `s.recalled`). Recalled tiles are never put in found/credited, so history, the score and every counter ignore them. While drilling (`s.drill`): only the drilled tiles match; the view is forced to Collapse on that section (the saved preference is untouched); bold blue "Drill mode" text replaces the Collapse | Expand toggle; the page background and grid turn blue (animated, via registered `--bg`/`--grid` and `body.drilling`); the Reveal button becomes a blue "End drill"; the drilled section's `↺` is shown pressed and disabled and other sections hide theirs; the answer box and Hint stay enabled (Hint applies to the drilled section). The drill ends through End drill (`endDrill`), or by itself (with confetti) once every drilled tile is recalled. Unanswered drilled tiles are then shown purple with a dashed border (`s.shown`) and can be drilled again. It also works on a finished round without re-committing it.

## Systems review

`systems-review.json` (one top-level key `Systems review`) has one drill per system or clinical context (Cardiovascular ... Psychiatric, plus Cancer x4, Post-operative early/late, Pre-operative assessment, Older person, Palliative care, Child, Infection and travel, Pregnancy). Each has `prompt` and one section, `symptoms` (stored as `symptoms to ask about`): `{"<symptom cluster>": [{label, keywords}]}`. Cluster names are free-form per drill (no `categories.json` vocabulary; `check:categories` only checks the shape) and drive the Hint boxes. Drill names must not contain ".". Keywords follow the same rules as below; keep generic single words (pain, fever) off specific tiles, since every tile whose keywords match the typed text is credited.

## JSON format

These files are seed data now (see above) and keep their original shape (a `prompt` and one key per section, such as `risks`). The stored quizzes were converted by `migrations/0006_free_form_sections.sql` to `{system, name, items: {"<section name>": {"Category": [items]}}}` with sections named `presentation`, `risk factors / etiology`, `examination findings`, `investigations`, `medications, treatment, and management` (conditions), `differentials`, `associated features (history)`, `investigations` (presentations) and `symptoms to ask about` (systems review); `mode` and `prompt` were dropped, and `migrations/0008_drop_quiz_system.sql` later dropped `system`. `lib/data.js` reads the stored shape.

`conditions.json`:

```json
{
  "<system>": {
    "<condition>": {
      "prompt": "Symptoms to ask about",
      "presentation":   [ { "label": "...", "keywords": "a|b|c" } ],
      "risks":          [ ... ],
      "examination":    [ ... ],
      "investigations": [ ... ],
      "medications":    [ ... ]
    }
  }
}
```

`presentations.json` has the same shape with a single system (`Presentation`) and the keys `differentials`, `associated`, `investigations`. For broad presentations the Differentials section holds conditions to screen for, risks, complications or injuries (see the `prompt`).

- **Top-level key = system / category** (e.g. `Cardio`, `Resp`, `Renal`, `GI`, `Endo`, `Rheum`, `Neuro`, `Vasc`, `ID`, `Breast`, `Ortho`, `Derm`, `Eye`, `ENT`, `Cross`). Each becomes a filter chip. Chip order = key order in the file. `Cross` holds cross-cutting histories (e.g. "Smoking history"). Systems apply to `conditions.json` only.
- **Second-level key = condition name**, shown as the title and in the "Or pick one" list. Must be unique within a system. List order is by system (in file order), then condition (in file order).
- **`prompt`**: required string (usually "Symptoms to ask about" or "History to ask about"). Shown under the title; may be empty ("").
- **`examination`**: signs a clinician would look for or elicit on examination (general, system-specific, relevant special tests). Examination items often share terms with presentation items (e.g. "oedema"); a shared term ticks both, which is accepted.
- **Sections**: every key for the file must be present, shown in the order above; an empty one renders "None listed for this condition." A section is either a plain array of items (one unnamed category) or an object `{"Category": [items]}` whose key order is the category order (`lib/data.js` accepts both). Items are flattened in category order, and tiles are numbered 1..n within each section in that order. Empty categories are omitted. Every item sits in exactly one category.
- **Item `label`**: text revealed on the tile (and the answer shown on reveal). Rendered as plain React text (escaped), not HTML.
- **Item `keywords`**: a single string of `|`-separated alternatives, compiled by `rx()` in `lib/match.js` into a case-insensitive regex. Each alternative is a regex fragment (so `.`, `.*`, `.?` work, e.g. `"ex.?smok"`, `"wake.*breath"`), and is prefixed with `\b`.
  - Alternatives of 3 chars or fewer (after trimming trailing spaces) are matched as whole words (optional plural `s`), and during live typing must be followed by a delimiter, so `ed` doesn't fire while typing `edema`. Alternatives longer than 3 chars are prefix matches (`orthop` matches `orthopnoea`), so use stems.
  - A leading `~` matches anywhere instead of at a word start (drug suffixes, e.g. `~pril`). Alternatives starting with a non-word character are used as raw regex.
  - Don't use `(`, `)`, `[`, `]` or `\` unless you intend regex syntax; never put a literal `|` inside an alternative.
  - Once an answer fires (live, after the 0.7s pause, or on Enter), **every** tile whose keywords match the text is credited, not just the best one, so a tile keyed on `swell` still gets `swelling` when another tile is keyed on `swelling`. Already-named tiles flash yellow only when no new tile matched. The earliest-then-longest match (the strict winner) only decides whether to wait: if the typed text is still a proper prefix of a longer literal keyword of another tile, found or not (e.g. `sputum` vs `sputum culture`), nothing fires while typing; after a 0.7s pause it credits the new tiles, but never flashes yellow for an already-named one (Enter still does). Consequence: a generic keyword on one tile also credits it whenever a more specific tile is typed (`sputum` tile and `sputum culture` tile both fire on "sputum culture"), so keep generic words off tiles that shouldn't be credited by them.
  - Abbreviations: `ABBR` in `lib/match.js` maps common abbreviations (htn, af, ckd, ...) to full terms. It is only tried when the typed text matches no tile, and while typing only after the 0.7s idle pause (so `ra` can't fire mid-`radiotherapy`). A keyword that already contains the abbreviation takes precedence. Add new entries to `ABBR`; avoid ambiguous ones (pe, mr, pd, ca, ed, us, cf).
  - Synonyms: `lib/synonyms.js` lists groups of interchangeable terms (erythema / redness, fever / pyrexia, kidney / renal, ...). Same fallback rules as `ABBR`: tried only when the typed text matches no tile, and while typing only after the idle pause. Whole words / phrases only; keep groups specific. Add a group there rather than widening individual tiles' keywords when the equivalence is general.
  - Where one word could name both a diagnosis and its test (iron, B12, electrolytes, urate), the diagnosis tile needs a qualifier (e.g. `iron deficiency`).

## Hint

Off by default; a "Hint" button beside Reveal (a checkbox toggle button, aria-pressed) toggles category boxes (`fieldset.cat` with a `legend`, wrapping flex, `.cats` in `recall-drill.css`) around the tiles of the current section only: the one Reveal names, or the open one when collapsed (`hintCode` from `useDrillGame`). Other sections stay flat, except that a complete section (every tile named, credited, ignored or revealed) always shows its category boxes, hint or not. The button is disabled when that section has no named categories and hidden once the round is over. `hint` lives in the round state (`s.hint`) as the code of the section it was switched on for; it only applies while `hintCode` still equals it, so completing that section (by typing or Reveal) or moving to the next hides it again and the next section isn't spoiled. It resets on every round/restart and is never saved. Tile index, number, matching, scoring, ignore and saved keys are unaffected.

## Category vocabulary (strict)

Every section in both JSON files is `{ "Category": [items] }`, and every category name must come from `categories.json` (per file, per section; list order = display order, each entry has a one-line `def` assignment rule). Categories appear only for entries that use them; single-item categories are allowed; there is no "Other". Items keep their original relative order within a category.

- To add or rename a category: edit `categories.json` first, then reassign items, then run `npm run check:categories` (it fails on any out-of-vocabulary or out-of-order category, empty category, or malformed item). It must pass before committing JSON changes.
- Conditions presentation also has **Acute on chronic** (just before Complications): features of an acute exacerbation / decompensation on top of the chronic disease (HF exacerbation, uraemia in CKD, COPD exacerbation, DKA, adrenal crisis). Conditions medications ends with **Avoid**: drugs, interventions and behaviours to avoid or use with caution (e.g. nitrates in aortic stenosis, NSAIDs in HF / CKD), named with the reason. Both are used only where they are a standard high-yield teaching point, not on every condition. Precipitants of decompensation stay under risks / Triggers.
- Conditions presentation includes the special cases Prodromal and Postdromal (used only where they fit); all neurological symptoms (motor, sensory, autonomic, bulbar) go under Neurological. Head and neck examination findings go to Neurological (eye, vision, hearing), Cardiorespiratory (JVP) or Local and peripheral signs (mouth, ENT, thyroid, nodes). Presentations differentials: when an item's mechanism is unambiguous (pneumonia, lung cancer, PE) use the mechanism category (Infective, Malignant, Vascular), otherwise the organ system. Presentations investigations share the conditions investigations list.
- Tool-assisted remapping (subagents): they may only use vocabulary names and must report items that fit nothing as vocabulary gaps rather than inventing categories.

## Editing guidelines

- Content lives in the database. Editing the JSON files changes nothing in the app (and `migrations/0003_seed_builtin.sql` is generated once and never regenerated, so ids stay stable). To change a built-in quiz use the quiz editor (or `PUT /api/quizzes/:id`).
- `npm run check:categories` still validates the JSON files' shape and category vocabulary; use it if you edit them for a future re-seed.
- When writing quiz `data` by hand keep it valid JSON; items have no ids or ordering requirement beyond position. Saved progress identifies an item by its label alone, so don't reuse a label within a quiz.

## Code notes

- `lib/data.js` `drillFromQuiz(quiz)` turns a quiz from the API (`{id, owner, forked_from, data}`) into the game's drill `{key (the quiz id), name, owner, forked_from, deleted, sections:[{name, icon}], items:[{label, keywords, section, cat, key (the label), re, lits}]}`. `section` is the section name (the key in `items`) and `cat` the category name or `null`; the game addresses sections by name. A `re` regex and literal keyword list (`lits`, for deferral) are attached to each item; `judge()` picks the tile(s). The API stores quiz data as sent, so malformed items (non-string label or keywords, an invalid regex) are skipped and a quiz without any section gives no drill. Results are memoised per quiz object, so regexes compile once. `lib/content.js` loads and remembers API responses for the session, except quizzes: `useQuiz` always reads from the server (`useLoad`'s `fresh` option), and `Drill` keys `QuizDrill` on `location.key` so every navigation (play, Next / New, the editor and back) remounts it and loads the quiz again. `Run` holds the stored quiz body (`quizData`) across restarts, so tile Edit / Delete keep building on the latest saved version.
- Section header icons are 16x16 pixel-art SVGs in `assets/` (`presentation.svg` thermometer, `risks.svg` warning triangle, `examination.svg` magnifying glass, `investigations.svg` flask, `medications.svg` pill), imported as URLs and drawn as a CSS `mask` filled with `--teal`, so they follow the theme. Each is one `currentColor` path of 1px rects with `shape-rendering="crispEdges"`; they render at 24px (1.5x the 16px heading text), which is sharp on 2x/3x screens but slightly uneven at 1x; 32px is the next exact integer scale.
- The header logo (`components/MedpunkLogo.jsx`, see DESIGN.md) is the exception to the mask-icon rule: it is animated and themed, so `assets/medpunk-logo.svg` is inlined with `?raw` and coloured by CSS classes (`.mp-pill`, `.mp-word`, `.mp-caret`, `.mp-check`). The letters are path outlines (no font), animated by one group's translate and scale. The component renders an empty fixed-size box first and inserts the SVG in an effect, because inserting it is what starts the animation.
- Expanding (the Expand toggle, or Reveal ending the round) scrolls the section just revealed or left open into view (`scrollTo` ref in `routes/Drill.jsx`; typing the last item does not scroll).
- Typography uses Apple system fonts with Inter as a fallback; no external requests.
- Colour variables are in `:root`, with light/dark via `prefers-color-scheme`.

## Accounts

Optional: sign in with Google (Better Auth, `worker/auth.js`); anyone with a Google account can sign up. The drill defaults to "Guest: nothing is saved" (ignoring a tile still works within the round). The header "Log in" link opens `/login` (`routes/Login.jsx`), a "Sign in with Google" button; new users land on `/settings` (`routes/Settings.jsx`) to choose an optional username (3-30 of `A-Za-z0-9_-`, unique, case-insensitive), otherwise the Google name is shown (`displayName()` in `lib/auth.js`). The header shows the Google avatar (`referrerPolicy="no-referrer"`) and the display name, which together with the arrow form one button; clicking it opens a dropdown with Settings and Log out (Escape, a click outside or navigating closes it). `/settings` stacks two old-macOS-style preferences panes (`.pref`), each a title strip then rows with the heading in the left column and the content on the right (under 600px each row stacks). The **Profile** pane has Account, Username and Session rows. The **Settings** pane holds the _global_ settings, shared by every user and stored in the `settings` table (`migrations/0005_settings.sql`, one JSON row per key): an Agent quiz prompt textbox (the instructions the quiz editor's Agentic tab gives an AI assistant; empty until someone saves one; the Agentic tab's brief then leaves out its Instructions part), an Agent quiz example textbox (a whole quiz pasted as JSON, in a monospace box; blank by default; the Save button refuses text that isn't valid JSON; stored as pasted, and the brief shows it as one line) and the editable Categories list (a vocabulary of names for the quiz editor's picker and Agentic tab, not an API rule; edited as a textbox with one per line and stored as an array; defaults to the unique names in `categories.json`). `GET /api/settings` is public and returns `{agentQuizPrompt, agentQuizExample, categories}` (stored rows over defaults); `PUT /api/settings` (approved editors only, rate-limited like history) replaces only the keys sent (`worker/settings.js` validates them). Each row has its own Save. `/privacy` (`privacy.html`) and `/tos` (`tos.html`) are the privacy policy and terms of service linked from the Google consent screen (both use `components/LegalPage.jsx`).

- `worker/app.js`: the host-agnostic API (Hono) taking `getAuth(c)` (a Better Auth instance), `getStore(c)` (`getHistory(userId)` / `putHistory(userId, rows)`) and an optional `limitWrites(c, key)`. `/api/auth/*` is Better Auth; `GET /api/history` returns the signed-in user's record and `PUT /api/history` replaces it (401 with no session, 403 for a cross-origin write, 429 over 60 saves a minute per user). The user is always the session's `users.id`, never a client claim. `worker/auth.js` builds the Better Auth instance per request (Workers expose bindings only per request): D1 binding `DB`, Google provider, `username` and `admin` plugins, UUID ids, database-backed rate limits. `worker/history.js` maps the client record to `history` rows and validates it; `worker/d1-store.js` is the D1 adapter; `worker/index.js` the Worker entry. Only `/api/*` and the old `/recall-drill/*` paths run the Worker (`run_worker_first` in `wrangler.jsonc`); everything else is static assets. To host elsewhere, mount `createApp({getAuth, getStore})` with another store adapter and serve `index.html` for unmatched paths.
- Storage is the D1 database bound as `DB`; the schema is in `migrations/` (applied with wrangler, no lazy table creation): Better Auth's `users`, `sessions`, `accounts`, `verifications`, `rateLimits`, and `history(user_id, quiz_id, data, updated)`, one row per user per drill (`data` is the drill record plus `starred`; a starred drill never played is `{"starred":true}`). `quiz_id` is the quiz's id (`migrations/0004_history_quiz_ids.sql` rewrote the old `mode|system|name` keys, stars included, to the built-in quiz ids; rows whose key matched no quiz were left alone and are ignored). The legacy username accounts became placeholder users (id = old username, email `<name>@legacy.invalid`); `scripts/claim-legacy.example.sql` moves one onto a real Google account.
- Secrets and vars: `BETTER_AUTH_URL` and `GOOGLE_CLIENT_ID` are `vars` in `wrangler.jsonc`; `GOOGLE_CLIENT_SECRET` and `BETTER_AUTH_SECRET` are Worker secrets (`npx wrangler secret put <NAME>`). For local dev copy `.dev.vars.example` to `.dev.vars` (gitignored). Google redirect URI: `https://medpunk.oyc.id.au/api/auth/callback/google`; only that origin can sign in (not `workers.dev` or preview URLs). Google's OAuth app is published to production; admins are set with `UPDATE users SET role='admin' WHERE id=...` in the D1 console.
- `lib/storage.js`: `fetchHistory`/`putHistory` and a localStorage hint (`recallDrillSignedIn`) so only likely-signed-in loads wait for the saved record; `AccountProvider` (`useSession()` from `lib/auth.js`) loads it whenever the session user changes (the drill route waits for that, as it needs the record).
- Record shape: `{v:1, stars:[quizId], drills:{quizId:{runs,last,score,found:["label"],credited:[...],ignored:[...],attempts:[{t,score,found,credited}]}}}`. `attempts` (oldest first, newest 30 kept) is the history; `runs/last/score/found/credited` mirror the latest attempt (`syncLatest` in `lib/storage.js`, call it after changing `attempts`), so the quiz list, the home counter and plain Redo incorrect read them as before. `fetchHistory` turns an old record (`runs>0`, no `attempts`) into one attempt. No D1 migration: the row is a JSON blob. Items are keyed by their label alone (migration 0006 stripped the old `X:` section prefix), so renaming a label in a quiz orphans its saved state.
- `AccountContext` saves with a debounced whole-record `PUT` (`mutate()` then `save()`/`flush()`): on finishing a round, on credit toggles after finishing, on star and ignore toggles, and on Menu/Back.
- Ignored tiles (missed tiles and purple drill tiles offer the `−` bubble on hover or tap, and so do correct (typed or credited) tiles once their section is complete, i.e. every tile in it is named, credited, ignored or revealed; press it again to restore) stay visible but greyed, count as already named when typed, and are excluded from the score and counters. They are always prefilled on the next attempt.
- Every drill row (guests too) shows a popover on hover, tap or right-click; clicking a row never starts the quiz. Entries are `.subbtn` buttons (icon, small black label). A drill with history has "Start from scratch", "Redo incorrect" and "Clear attempt"; one without has "Start quiz"; signed-in users also get "Star" / "Unstar" and "Edit". Redo incorrect navigates to the drill with route state `{inc:true}` (the latest attempt) or `{inc:{found, credited}}` (a given attempt, from the history panels): found and credited tiles are prefilled, so only the blanks remain. Both options record the result: a redo round carries the saved found and credited forward, so the saved score is the combined score, and it is added as a new attempt. Start from scratch begins blank (ignored tiles are still prefilled) unless the quiz has an autosaved round, which it resumes or asks about. On the done screen, logged-in users get an "Add to history" checkbox (ticked by default, unticked after Redo / Retry incorrect, so those rounds are not recorded unless the user ticks it; a ticked round is saved and `flush()`ed immediately). Unticking restores the drill's attempts to how they were before the round (`prevRec`, a copy of the whole record) and re-ticking saves the round again, each flushed at once; while unticked, credit toggles don't touch the record (ignored tiles still save). The done screen also has "Retry incorrect" (hidden when nothing was missed): it restarts the drill with the tiles found or credited in the round just played prefilled, via `restart({found, credited})` (a new `useDrillGame` round), so it works for guests too and, for accounts, records like Redo incorrect. A starred row shows a plain ★ (not clickable); starring is done from the row menu. Logged-in users also get a History panel to the right of the list (below it on narrow screens): one row per attempt (so a quiz can appear several times), most recent first, showing score, name and date. Hover, tap or right-click a history row for the same pop-up menu as the quiz list (`.cell` > `.menu`, via `DrillActions` and the shared `useRowMenu` hook in `lib/useDrillUi.js`): Start from scratch / Redo incorrect (of that attempt) / Clear attempt / Edit, without Star. "Clear attempt" (confirm first) removes that one attempt (`syncLatest` then re-mirrors the newest remaining one); ignored items and the star are kept. The quiz page has its own History (`components/QuizHistory.jsx`, signed in and at least one attempt): a "History" toggle under the tiles panel, closed by default, that opens a grid of this quiz's attempts (score and date, newest first) whose menu has only Redo incorrect and Clear attempt. It sits at the bottom of the screen when the tiles panel is short (`.main` is at least a screen tall and `.qh` has `margin-top:auto`), else straight after the tiles.
- Autosave (signed-in users): a round in progress is backed up as it is played. A correct answer (typed, or credited with "I got this"), a reveal, ignoring a tile and deleting an item (`autosave()` in `useDrillGame`) call `account.saveProgress(quizId, snapshot)` (nothing else saves: not the Collapse/Expand view, Hint, drills, Start again or Resume), which debounces 1.5 s and `PUT`s `/api/progress/<quizId>` (table `quiz_progress(user_id, quiz_id, data, updated)`, `migrations/0010_quiz_progress.sql`; `worker/progress.js`; also `GET /api/progress` for `{quizId: {updated, got, total}}`, `GET`/`DELETE /api/progress/<quizId>`). The snapshot holds `found`, `credited`, `revealed` and `ignored` as item labels (like history), `active`, `redo` and the counts `got`/`total`; drills (`drill`, `drilling`, `recalled`, `shown`) and the hint are never saved. It is flushed when the tab is hidden (`keepalive`) and when the game unmounts. Finishing the round deletes it (`apply` sees `over`), and so does a round with nothing found yet (`got` is 0; such a save is also dropped when opening the quiz, never offered for resuming), so does Redo incorrect (`useStart` sends route state `{inc:true, fresh:true}`; `Start` clears `fresh` from `history.state` once it has acted on it, so a reload or Back does not replay it and delete the round played since). `AccountContext` loads the list with the history and exposes `progress`, `saveProgress`, `dropProgress`, `flushProgress`. Opening a quiz that had progress (`Start` in `routes/Drill.jsx`, decided once per navigation) fetches the snapshot: saved within `RESUME_AFTER` (5 min, currently 20 s while testing; `lib/progress.js`, compared with the browser's clock against the server's `updated`) restores it silently; an older one shows the saved round locked, with `components/ResumePrompt.jsx` over the play area (`.tiles.veiled`: the dim sits over it and only the text inside the tiles is transparent, so the silhouette shows while headings and counters stay readable; `.resume-veil`): **Start again** drops the snapshot and swaps in the blank round, **Resume (got/total)** unlocks the saved one. The menus have no Resume entry: **Start quiz** and **Start from scratch** open the quiz without `fresh`, so they resume or ask (a quiz with no autosave starts blank), while Redo incorrect discards the progress. Progress is also flushed on `pagehide`, as Safari does not reliably fire `visibilitychange` on reload. Saves are best effort and silent.

Local dev: `npm run dev` only; `@cloudflare/vite-plugin` runs the Worker and a local D1 (`.wrangler/`) inside the Vite dev server; apply the schema locally with `npx wrangler d1 migrations apply practicals --local` and put dummy values in `.dev.vars`. Google sign-in cannot complete on a cloud dev server (Google redirects to the browser's `localhost`); the real login is only testable on the deployed site. Production uses the D1 database whose id is in `wrangler.jsonc` (previews share it); keep the Worker name `practicals` to match the Workers Builds project. Production migrations are applied by hand: back up with `npx wrangler d1 export practicals --remote --output backup.sql`, then `npx wrangler d1 migrations apply practicals --remote`.

## Quizzes and playlists (API)

Users can own **quizzes** and **playlists** (ordered, sectioned lists of quiz references). Everything is readable by anyone, including guests; only the approved editors (see "Editing permissions" below) can create, edit, soft-delete, restore or fork a quiz and create, edit, copy or delete a playlist. The UI reads this API: Home shows the three built-in playlists, Playlist and Drill load from it, and History resolves its quizzes with `GET /api/quizzes?ids=...&full=1`. The playlist page has an Edit button for signed-in users (`components/PlaylistEditor.jsx`, @dnd-kit): title, description, a **New quiz template** card (the sections new quizzes start with, laid out like the quiz editor's Sections card: a drag handle (reorders the template), an editable name and a red Delete per row, then "Add section"; stored as `quiz_settings.sections`, see below) and sections (add, rename, reorder) with quiz rows dragged by their handle within or between sections. Hovering a quiz row (or focusing it; always on touch) shows a red **Delete** button: it asks with the custom confirm dialog, then takes the quiz out of the list and into the editor's `removed` list; nothing is saved until Save, which saves the playlist without it and then soft-deletes each removed quiz with `deleteQuiz` (`lib/content.js`; a quiz that was already deleted is only removed from the playlist). If a delete fails the editor stays open with the message, keeps the failures, and pressing Save retries them. Cancel brings the rows back. The quiz editor (`components/QuizEditor.jsx`, route `/q/<id>/edit`) opens from the pencil on the drill page, the Edit entry in the quiz popover (also opened by right-click) and the history panel; Manual tab: per section (each section's title is an editable heading with ↑ Up / ↓ Down; a section with no categories also offers Delete section, and an "Add section" button appends a blank one; names must be non-empty and unique, and a quiz needs at least one section; sections are held by a stable id so a rename keeps its categories), categories (hint column; "New category" opens a modal, `components/CategoryPicker.jsx`, to select one of the global categories from Settings that the section doesn't use yet, then Add; a filter box narrows the list; a "Custom category" textbox at the bottom of the (scrolling) list takes any other name for this category only, never added to the Settings list, and can't repeat a category the section already has; each category has ↑ Up / ↓ Down buttons (one row) and an Edit button (the next), which opens the same picker to change its name) with items (label plus comma-separated matches stored as `a|b|c`), a dotted "New item" gap between items and a delete button; the Agentic tab (`components/AgenticTab.jsx`) is a copy-paste workflow with an AI assistant: a **Sections** card under "How to use" (same rows as the playlist's default sections, `.defsecs`: an editable name, a red Delete and "Add section"; they are the editor's own `sections` state, so the Manual tab and the brief follow; Delete is always shown but disabled, with an instant hover popover (`.qe-tiptext` on its wrapper span, shown below the button, dark in both themes; a `title` tooltip is delayed) saying why, unless the section has no categories; while a section is unnamed or the quiz can't be built, `problem` is shown, the brief is not built and Copy is disabled), then read-only instructions (`lib/agentBrief.js`: up to five fenced/coloured parts, the global **Agent quiz prompt** from Settings verbatim as the instructions, the Settings categories as a one-line JSON list, the Settings **Agent quiz example** as an **Example quiz** part (left out when blank) with a note above it that the items will differ and the schema below must be followed strictly, a **Schema** (an example of the quiz format with a line per current section, rebuilt live from the Sections card), and the quiz's current JSON; it scrolls both ways; it is a toggle, closed by default; the prominent Copy instructions button sits under it and copies all the parts plus a closing `Make this change:` line; secondary ChatGPT → / Claude → / Gemini → buttons beside it copy the same text and open that tool's chat page in a new tab), a monospace box to paste the AI's JSON into, and Validate / Apply buttons that first parse the JSON, then check on the client that the sections are exactly the quiz's current ones (`sectionErrors`: none added, renamed or dropped; order is free) and every category is in the Settings list (`categoryErrors`; both in `lib/content.js`; the Agentic tab is the only strict place, so an AI must keep to the list), and then let the server check the rest (below); Apply (the Agentic tab's Save) loads the checked JSON into the editor's Manual state (name, sections, categories, items and the quiz's other fields), clears the box and switches to the Manual tab with an "Applied" note, saving nothing: Save on the Manual tab does that. With the box empty, Apply (which stays enabled) shows the error "JSON text box is empty."; Validate is disabled until there is JSON. Both editors (quiz and playlist) are forms whose only way to save is the Save button (Apply on the Agentic tab): Enter in a text box does nothing (`lib/noEnterSubmit.js` on the form's `onKeyDown`; the Category picker's own Enter still picks the category). The editor has a page heading above the tabs: an "Edit quiz:" label (same font and size, accent colour) followed on the same line (`.qe-namehead`) by the quiz's name as an editable textbox with only a 2px bottom border as long as the text (black, accent colour while focused; `.qe-pagename`; it is the quiz's name on both tabs; there is no separate Name field). A quiz has no `system` (migration `0008_drop_quiz_system.sql` removed it; the group a quiz belongs to is the playlist section that lists it). The playlist page's **New quiz** button (beside Edit, signed-in users) opens `components/NewQuizDialog.jsx`: a name (focused, placeholder `quiz-name-here`) and the playlist section to put it under (first one preselected; it needs default sections in the New quiz template and at least one playlist section, else Create is disabled with a note). Create runs `createQuiz` (`POST /api/quizzes` with an empty section for each template name) and then `addQuizToPlaylist` (re-reads the playlist, appends the id to the end of the chosen section and `PUT`s it; if that second step fails the dialog keeps the quiz id, so trying again doesn't make a second quiz), then navigates to `/q/<id>/edit` with route state `{tab: "agentic"}`, which `Drill` passes to `QuizEditor` as `initialTab`, so the quiz opens on the Agentic tab with the template's sections. There is still no UI to fork or delete quizzes, or to create, copy, fork or delete playlists; the API for all of them exists. A quiz body is checked by `validateQuiz` in `worker/content-util.js` (shape, keywords that compile and no unknown fields; **category names are not checked**, so Systems review quizzes, whose cluster names aren't in the Settings list, save and can be edited normally; the client enforces the list only on the Agentic tab) and is otherwise stored as sent, except that the Worker owns a quiz's `deleted` flag. `POST /api/quizzes` (create) and fork don't validate yet.

- Tables (`migrations/0002_quizzes_playlists.sql`): `quizzes(id, owner_id, forked_from, data)` and `playlists(...)`, the same columns; `quizzes` also has `deleted` (0 or 1, the soft-delete flag; `migrations/0009_quiz_deleted_column.sql` moved it out of `data`). Ids are UUIDv7 strings (`uuid`), so `ORDER BY id DESC` is newest first and there is no `created_at`. `owner_id` references `users(id)` with `ON DELETE RESTRICT` (a user who owns content can't be deleted; Better Auth's user deletion is off); `forked_from` is `ON DELETE SET NULL`. D1 enforces foreign keys.
- `quizzes.data` is the drill (`{name, items: {"<section name>": {"Category": [items]}}}`; section order is the key order). A quiz's legacy history key was `mode|system|name` (see migration 0004). `playlists.data` is `{title, description, quiz_settings:{sections:[name]}, sections:[{title, quiz_ids:[quizId]}]}` (`quiz_settings.sections` are the default section names for new quizzes in the playlist; for now they are only stored, existing quizzes never change, and a playlist without them reads as an empty list; `PUT` replaces the whole data, so the editor always sends them); a quiz id should appear once per playlist.
- Built-ins (`migrations/0003_seed_builtin.sql`, generated once by `node scripts/seed-builtins.mjs`, which refuses to overwrite it so ids stay stable): the 187 drills as quizzes and three playlists (Conditions, one section per system; Presentations; Systems review), owned by the placeholder user `ollie` (`scripts/claim-legacy.example.sql` hands ownership to a real account). Editing `conditions.json` etc. does not change these rows.
- Routes (`worker/quizzes.js`, `worker/playlists.js`, shared helpers in `worker/content-util.js`; all JSON). Writes need a session and a same-origin request (401 / 403); the owner-only ones (deleting a playlist) include `AND owner_id = ?`, and any write that changes nothing returns 404, so "missing" and "not yours" look the same.
  - `GET /api/quizzes`, `GET /api/playlists`: summaries (quizzes: `name/deleted`; playlists: `title/description/sectionCount`) with `owner: {id, name, image}` (never email), newest first, `?owner=me|<id>`, `?before=<id>&limit=<n>` (max 100) paging via `next`. Deleted quizzes are hidden unless you ask for your own with `?owner=me&deleted=1`. More filters: `?ids=<id,id,...>` (up to 100, with `&full=1` to include each quiz's `data`), `?name=` (exact). Public reads (everything except `owner=me`) carry an ETag and `cache-control: no-cache`, so an unchanged playlist revalidates with a 304; all other responses are `no-store`.
  - `GET /api/quizzes/:id` (deleted ones too; the quiz is `{id, owner, forked_from, deleted, data}`, with `deleted` at the top level as in the summaries), `POST /api/quizzes` (body = the data; a `deleted` key is dropped, a new quiz is never deleted), `POST /api/quizzes/validate` (editors only; the same check as PUT without saving: 200 `{ok:true, summary}` or `{ok:false, errors:[...]}`), `PUT /api/quizzes/:id` (editors only; body checked by `validateQuiz`, a failure is 400 `{error, errors}` with one message per problem; replaces the data and leaves the `deleted` column alone; every playlist that references the quiz sees it), `PUT /api/quizzes/:id/deleted` (`{"deleted":true|false}`; editors only; playlists are untouched, so restoring brings it back everywhere), `POST /api/quizzes/:id/fork` (your own copy, `forked_from` set, not deleted).
  - `GET /api/playlists/:id`: the playlist (with `quiz_settings`) and its quizzes grouped by section in order, deleted quizzes included with their flag; `?quizzes=meta` leaves the quiz bodies out (the Conditions playlist is about 320 KB in full, 20 KB as meta). `POST /api/playlists`, `PUT /api/playlists/:id` (replaces the data; editors only, body validated as `{title, description, sections:[{title, quiz_ids}]}` plus an optional `quiz_settings:{sections}` whose names must be non-empty, trimmed and unique ignoring case), `DELETE /api/playlists/:id` (hard delete, quizzes untouched), `POST /api/playlists/:id/copy` (same sections and quiz ids, quizzes not copied).
  - `POST /api/playlists/:pid/quizzes/:qid/fork`: fork a quiz and swap the fork into your own playlist at the same place, in one `db.batch()` (the copy is inserted only if you own the playlist, and the playlist is updated only if the copy exists, so neither half can happen alone). Returns the new quiz.
- No quotas, size limits or moderation endpoints exist yet; D1's 2 MB row limit is the only cap.

## Editing permissions

Changing shared content (quizzes, playlists, the global Settings) is limited to a hard-coded list of verified Google emails in `worker/permissions.js` (`canEdit(user)`: lower-cased email in the list, `emailVerified`, not banned). Emails, not user ids: ids are random UUIDs created at first sign-in. The list never reaches the browser.

- Server: the `editor` middleware in `worker/app.js` (`auth`, then `canEdit`, else 403 `{error:"editor_only"}`) guards every content write: quizzes (create, validate, `PUT`, `deleted`, fork), playlists (create, `PUT`, delete, copy, fork) and `PUT /api/settings`. Personal data stays on plain `auth` for any signed-in user: `/api/history` (stars, ignored items, attempts) and `/api/progress`.
- Client: `worker/auth.js` adds the `customSession` plugin, so `GET /api/auth/get-session` returns `user.canEdit`; `AccountContext` exposes `canEdit` and `sessionPending`. Edit entries (tile menu Teach / Edit / Delete, the Edit pencil and quiz-popover Edit, New quiz, playlist Edit, the Settings pane) show only when `canEdit`. Ignore, I got this, Star, Redo incorrect and Reset progress are for everyone signed in.
- `components/RequireEditor.jsx` wraps each edit page and modal (`/q/:id/edit`, the playlist editor, New quiz, the tile Teach/Edit dialog): it waits for the session, then for a non-editor opens the Access denied dialog and calls `onDenied` (leave or close). `AccessDeniedListener` (in `App.jsx`) opens the same dialog when `lib/api.js` sees a 403 `editor_only`.
- To add an editor: add the email to `EDITOR_EMAILS` in `worker/permissions.js`.

## Unsaved changes

Both editors call `useLeaveGuard(dirty)` (`lib/useLeaveGuard.js`; dirty = the editable state differs from how it was on opening, or text is pasted on the Agentic tab, or rows were taken out of a playlist). In-app navigation (links, logo, Back) is held by `useBlocker` and asked with the custom dialog (Leave / Stay); Cancel goes through `guard.leave(fn)`; a successful Save calls `guard.bypass()` first. Closing or reloading the tab only gets the browser's generic `beforeunload` prompt (the text can't be customised and no dialog can be drawn). `useBlocker` needs a data router, so `main.jsx` uses `createBrowserRouter` with one catch-all route rendering `App`.

## UI conventions

See `/DESIGN.md` (secondary buttons, the tab slider, cards, dialogs, errors, the editable item card). Never use the browser's `alert()` / `confirm()` (some browsers, including the Claude built-in one, don't show them): use `useDialog()` from `components/Dialog.jsx` (`DialogProvider` wraps the app in `App.jsx`), e.g. `if (!(await confirm({message, unsafe: "Delete"}))) return;`.
